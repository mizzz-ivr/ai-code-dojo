## 目的

Workerが生成するapplication retryとstale recoveryを、`WORKER_QUEUE_CONSUMER=http|sqs`で選択中のqueue runtimeへ再投入する。

## 必須境界

- HTTPは既定値・rollback先として維持する。
- HTTP選択時はAWS clientを生成しない。
- SQS選択時はconsumer / retry producerで同一clientを共有する。
- Standard / FIFOをQueueUrlから判定する。
- FIFO group / dedup契約は既存SQS producerを再利用する。
- Worker runtimeはtransport共通`enqueue()` portを提供する。
- Application retryはruntime `enqueue()`を直接利用する。
- Stale scannerへruntime `enqueue()`を明示注入する。
- Process-global registrationや共有可変singletonを使用しない。
- Worker roleはsource queueへのReceive / Delete / ChangeVisibility / Sendだけとする。
- API producer roleはSendだけを維持する。
- DLQ read / purge / queue管理 / wildcard resourceを追加しない。
- QueueUrl / credentials / ReceiptHandle / raw attempt key / raw errorをログへ出さない。
- Processing lease / attempt fencing / completion guardを変更しない。

## 非対象

- ECS task definition / service / cluster
- SQLiteからmanaged DBへの移行
- 実AWS deploy / transport切替
- Durable retry scheduling
- DLQ replay / purge
- Metrics / dashboard / alert
- Runner / hidden tests / auth / UI

## レビュー観点

- Runtime enqueueの依存注入境界が明確か。
- Application retryとstale recoveryが同じruntimeを利用するか。
- Process-global mutable stateが残っていないか。
- SQS clientを重複生成・重複destroyしないか。
- Send失敗時にDB状態を成功扱いしないか。
- FIFO dedup keyがattempt単位で安定しているか。
- IAM action / resourceが完全一致で検証されるか。
- HTTP rollback時にSQS設定を要求しないか。
